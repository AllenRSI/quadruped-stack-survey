# 模型派控制器复现：站立成功，行走失败

> **执行日期**：2026-11-22 · **环境**：WSL2 Ubuntu / RTX 3060 Ti 8 GB / Python 3.12.16 / MuJoCo 4.0.1
> **状态**：真跑过，结果如下。这是一次**部分成功 + 部分失败**的复现，失败原因已定位到方法层面。

---

## 1. 复现了什么

不是论文数字的复现，而是**模型派控制器最小可行结构**的复现：

| 模块 | 实现 |
|---|---|
| 本体模型 | 自建 12 自由度四足 MJCF（`quad12.xml`，11.2 kg，腿长 0.36 m） |
| 机身力控 | 高度 PD + 速度 PD + 姿态 PD → 期望合力/合力矩 |
| 力分配 | 竖直力均分 + 横向力最小二乘 + 摩擦锥裁剪（μ=0.6） |
| 关节控制 | 支撑腿 τ = Jᵀf + 关节 PD（保持落脚点）；摆动腿 IK + PD |
| 步态 | 对角小跑，周期 0.5 s，占空比 0.6，Raibert 落脚点 |
| 控制频率 | 250 Hz（物理 2000 Hz） |

代码：[run_quad.py](run_quad.py) · 模型：[quad12.xml](quad12.xml)

## 2. 结果

### 2.1 站立（成功）

```
$ python run_quad.py --mode stand --dur 6
```

| 指标 | 数值 | 判定 |
|---|---|---|
| 是否摔倒 | 否（6 s 全程） | ✅ |
| 机身高度 | **0.2648 m**（目标 0.275） | 偏低 1 cm |
| 高度抖动 std | **0.0102 m** | 1 cm 级 |
| 最大滚转 | **4.5°** | ✅ |
| 最大俯仰 | **7.7°** | ✅ |
| 前后漂移 RMSE | 0.107 m/s | 可接受 |

**结论：站立控制可用。** 4 脚支撑下的力分配 + 关节 PD 能把 11.2 kg 的机身稳在 1 cm 抖动内。

### 2.2 小跑 0.4 m/s（失败）

```
$ python run_quad.py --mode trot --dur 10 --vx 0.4
```

| 指标 | 数值 | 目标 | 判定 |
|---|---|---|---|
| 是否摔倒 | 否（10 s 全程） | 不摔 | ✅ |
| 平均前进速度 | **−0.124 m/s** | 0.4 m/s | ❌ **方向都反了** |
| 速度跟踪 RMSE | 0.584 m/s | — | ❌ |
| 机身高度 | **0.1875 m** | 0.275 | ❌ 下陷 8.7 cm |
| 最大滚转 | 42.4° | <10° | ❌ 晃动明显 |

**结论：能保持平衡 10 秒不摔，但走不动——机身向下沉、净位移接近零甚至倒退。**

## 3. 失败诊断（这部分比结果更有价值）

调参过程中的两个可复现现象：

1. **力矩→足端力的符号不一致。** 用 `τ = −Jᵀf` 时，期望前向力 +7.2 N，实测机身速度却是 −0.26 m/s（往后走）。翻成 `τ = +Jᵀf` 后前向分量变对，但竖直分量又反向——提高高度增益 `kz` 反而让机身下沉更深（kz=400 → 高 0.151 m；kz=600 → 高 0.145 m）。**同一个符号不能同时满足两个方向，说明问题不只在符号。**

2. **高度增益越大，下沉越深。** 这是典型的「控制器在跟错误的状态空间较劲」：单纯力分配没有考虑腿的运动学约束（腿弯曲后竖直力臂急剧下降），力被腿的几何吃掉了。

**根因判断：**

- 论文里的 convex MPC 是**滚动时域优化**（预测时域 0.5 s、在线 QP），它同时决定未来 N 步的足端力与落脚点；我实现的是它的**一步版**（只解当前时刻的力分配）。
- 缺少 **WBC 的任务层级**：论文用分层 QP 处理「机身位姿 > 足端轨迹 > 力矩」，我只有并列的 PD 项，支撑腿的 PD 与力项互相打架。
- 缺少**真正的接触时序优化**：论文的步态与力是联合优化的，我的步态是写死的时钟。

**这不是"调参不够"，而是缺了方法本身的两个核心机制。** 继续调只会过拟合当前模型。

## 5. 下一步该怎么做

按性价比排序：

1. **补齐 WBC 分层**：把「机身位姿任务 / 足端轨迹任务 / 关节正则」做成严格优先级的分层 QP，而不是并列 PD。这是让腿走起来的最小改动。
2. **实现滚动时域 MPC**：预测时域 10 步 × 40 Hz，用线性化单刚体模型 + OSQP。论文口径下的 QP 规模是 12 状态 × 10 步，OSQP 单次求解应在毫秒级。
3. **换成论文同款模型**：本项目的 `quad12.xml` 是自建的，与 MIT Cheetah / Unitree 的质量分布差异大，数字不可直接对比。
4. **或者放弃自研，走 RL 路线**：这恰好印证了本调研的结论——2021 年之后大家不做手工 MPC 了，是因为它的工程量全在这些「符号、层级、约束」的细节里。
